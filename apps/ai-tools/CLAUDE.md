# CLAUDE.md

このファイルは、Claude Code が `apps/ai-tools/` で作業する際のガイダンスを提供します。

**会話は日本語で行う。**

## コマンド

```bash
yarn dev         # ローカル開発サーバー起動（:3000）
yarn build       # 本番ビルド（Cloudflare Workers向け）
wrangler deploy  # Cloudflare Workersへデプロイ
```

ローカルの環境変数は `.env` に記載する:

```
NUXT_OPENAI_API_KEY=...
NUXT_ANTHROPIC_API_KEY=...
NUXT_GEMINI_API_KEY=...      # whisper文字起こしでGeminiを選んだ場合のGoogle AI Studio鍵（未設定だとGemini選択時にエラー）
NUXT_MIYAKO_VECTOR_STORE_ID=...
NUXT_IPPON_PROVIDER=...   # ippon の3D生成プロバイダ（tripo|mock。未設定なら mock）
NUXT_TRIPO_API_KEY=...    # ippon で provider=tripo のときの Tripo AI 鍵（無ければ mock にフォールバック）
NUXT_ENCRYPTION_KEY=...   # marriage コメント・Google Healthトークン暗号化（32文字以上推奨）
NUXT_FITBIT_CLIENT_ID=...      # Google Cloud の OAuth 2.0 クライアントID（fitbit連携用）
NUXT_FITBIT_CLIENT_SECRET=...  # 同上シークレット
NUXT_FITBIT_REDIRECT_URI=...   # 例: https://<host>/api/fitbit/callback
NUXT_LIFE_GOOGLE_CLIENT_ID=...      # Google Cloud の OAuth 2.0 クライアントID（life連携用。fitbitとは別クライアント）
NUXT_LIFE_GOOGLE_CLIENT_SECRET=...  # 同上シークレット
NUXT_LIFE_GOOGLE_REDIRECT_URI=...   # 例: https://<host>/api/life/google/callback
NUXT_KIKIGAKI_GOOGLE_CLIENT_ID=...      # Google Cloud の OAuth 2.0 クライアントID（kikigaki連携用。life/fitbitとは別クライアント）
NUXT_KIKIGAKI_GOOGLE_CLIENT_SECRET=...  # 同上シークレット
NUXT_KIKIGAKI_GOOGLE_REDIRECT_URI=...   # 例: https://<host>/api/kikigaki/google/callback
NUXT_FARM_NEWS_ADMIN_KEY=...   # farm-news の手動実行API（/api/farm-news/run 等）を x-admin-key ヘッダーで守る秘密キー
```

### kikigaki（キキガキ）のGoogle連携セットアップ

**2026-09-04にDocs/Sheets/Tasks/Calendarへの承認送信フローをUIから外し、PDFダウンロードに置き換えた**
（当時のGoogle連携ボタン・承認ボタンはコメントアウトのまま残していた）。
**2026-09-07に、承認フローとは別物として「Googleドライブへの保存」機能を追加**した＝
PDFでダウンロードするたびに、ユーザーが設定したドライブのフォルダへ自動でコピーを保存する
（`index.vue` の設定欄で連携・フォルダ設定を行い、`[id].vue` の「PDFでダウンロード」を押すたびに
`api/kikigaki/google/drive-save.post.ts` が裏で呼ばれる。承認という概念は無く、ユーザーが
自分のPDFを自分のドライブへ置くだけの操作）。この追加にあわせて**スコープを `drive.file` だけに絞った**
（旧・承認フローが使っていた `documents`/`spreadsheets`/`tasks`/`calendar` は落とした）ため、
**旧フローの `writeApprovedMinutes` 以下（`kikigaki-google.ts`）・`api/kikigaki/approve.post.ts`・
`api/kikigaki/resend-sheet.post.ts` はファイルとして残っているが、今のスコープでは動かない**
（削除はしていないが動作は保証されない。再有効化するならスコープを戻し、全員に再連携してもらう必要がある）。

life / fitbit とは別に、Google Cloud で新規に OAuth 2.0 クライアントを発行する（**スコープが違うので使い回さない**）。

1. Google Cloud Console で「Google Drive API」を有効化
2. OAuth同意画面でスコープに `drive.file`（アプリが作成したファイルにのみアクセスする最小権限）を追加
3. OAuth 2.0 クライアントID（ウェブアプリケーション）を発行し、リダイレクトURIに
   `https://<host>/api/kikigaki/google/callback`（ローカルは `http://localhost:3000/api/kikigaki/google/callback`）を登録
4. `.env` に `NUXT_KIKIGAKI_GOOGLE_CLIENT_ID` / `..._SECRET` / `..._REDIRECT_URI` を設定
   （本番は3つとも `wrangler secret put` で登録する。REDIRECT_URI は秘密ではないので `[vars]` でもよいが、
   既存の `NUXT_FITBIT_REDIRECT_URI` が secret で入っているので揃えている）

※ **Google の公開ステータスは「テスト」ではなく「本番環境」にすること**。テストのままだと
リフレッシュトークンが7日で失効し、週明けに必ず連携が切れる（審査に出す必要はない。
未審査だと同意画面に「確認されていません」の警告が出るが、自分たちで使うぶんには問題ない）。

※ 保存先フォルダは**ユーザーが自分で用意した既存のGoogleドライブのフォルダ**を、共有リンクまたはIDを
貼り付けて設定する（アプリ側でフォルダを自動作成することはしない）。リンクからのID抽出は
`kikigaki-google.ts` の `extractDriveFolderId()`。D1（`kikigaki_google_connections`）が持つのは
リフレッシュトークン（暗号化）と、そのフォルダID・入力欄への表示用に貼り付けた文字列そのものだけ。

### news（AIニュース朝刊）のセットアップ

3日に1回 JST 7:00（news-digest、cron は UTC 22:00、day-of-monthステップ `*/3` での近似。
月をまたぐ境目だけ間隔が1〜2日ずれる）に収集・要約・分類を、その15分後（news-trends、UTC 22:15）に
潮流の考察更新を行う。**通知はしない**（メールは検討したがコストが見合わずやめた。読むのは `/news` ページ）。
新規の外部サービスは無く、既存の Cron Trigger / `WHISPER_DB` / `NUXT_ANTHROPIC_API_KEY` に相乗りしている。

**2つのタスクに分かれているのは Cloudflare Workers の subrequest 上限のため**（1回の呼び出しにつき
Freeプランは50個。外部への `fetch()` だけでなく D1 バインディング経由のアクセスも同じ枠でカウントされる。
`[limits] subrequests` で変更できるのはPaidプラン側で、Freeの上限50自体は設定では上げられない）。
15フィードの取得＋要約＋6潮流ぶんの考察更新を1回の呼び出しに詰め込むと簡単に超え、実際に
`Too many subrequests by single Worker invocation` で失敗した（2026-09-06）。今は
news-digest（収集・要約・分類）と news-trends（考察更新）を別のcron・別のAPIエンドポイントに分けて
呼び出しごとの予算を分けている。手動実行のページの「いま収集する」ボタンも内部でこの2つを順番に呼ぶ
（ユーザーには1回の操作に見せている）。詳しい設計は `src/server/utils/news-run.ts` の冒頭コメント参照。

初回セットアップはテーブル作成だけ:

```bash
wrangler d1 execute whisper-db --remote --file src/server/db/052_news.sql
```

**ソースの追加**は `src/utils/news-sources.ts` の `NEWS_SOURCES` に1件足すだけ（RSS 2.0 / Atom どちらも読める）。
`id` は D1 に保存される識別子なので、一度入れたら変えない。2026-09-06 時点で15フィード
（OpenAI・DeepMindの2社ブログ＋ロボティクス/農業/マーケ/計算基盤/地政学/安保/医療の13フィード）。

**潮流分類と考察**: 記事は要約と同時に `src/utils/news-currents.ts` の6潮流（フィジカルAI／農業・畜産とAI／
コーディング・マーケの自動化／半導体と電力の競争／軍事・サイバーとAI規制／メンタルヘルスとAI）のどれか1つにAIが分類する
（`news-ai.ts` の `summarizeArticle`）。ソースと潮流は固定対応ではなく記事ごとに判定する（IEEE Spectrumの記事でも
内容次第で「コーディング・マーケの自動化」になり得る）。**2026-09-12にタイトルを平易な言葉に付け替え、農業・畜産を
「フィジカルAI」の説明文から独立した6つ目の潮流として切り出した**（旧: 実世界に手を伸ばすAI／知的労働の自動化／
土台を巡る競争／安全保障とガバナンス／心と健康に触れるAI。id自体はD1に保存済みの過去記事を壊さないため変えていない
＝ラベル・説明文のみの変更）。**その日に新着があった潮流だけ**、直近30日分の見出し一覧（`NEWS_TREND_LOOKBACK_DAYS`）
と前回の考察を材料に `news-ai.ts` の `synthesizeCurrentNarrative` が「いまの考察」を書き直し `news_currents` に
保存する（履歴は持たず1潮流1行を上書き）。新着が無かった潮流は据え置き＝6潮流ぶん毎回呼ぶ無駄を避けている。
ページ上段の6枚のカードがこれで、クリックすると下の記事一覧がその潮流だけに絞り込まれる（大きな流れ→個別記事のドリルダウン）。

**考察は3章構成**（`TREND_SECTION_TITLES`＝ここまでの流れ／今日の新着／これから）で `NewsCurrentSection[]` として
`news_currents.narrative` 列に JSON文字列で保存する（列名はそのまま、中身の形式だけ変えた。章立て化する前の
プレーンテキスト1本の値が残っていても `parseSections()` が壊れずフォールバックする）。
**カード面には全文ではなく要点3つ（15字程度の短句）を出す**（2026-09-14追加。`synthesizeCurrentNarrative` に
`bullets` を同時に生成させ、`narrative` 列は `{ sections, bullets }` のオブジェクトとして保存する形に変えた
＝列名・保存場所は変えず中身の形式だけ拡張。`parseSections()`（`server/utils/news.ts`）は
配列のみの旧形式・オブジェクト形式・章立て化前のプレーンテキストの3種類すべてをフォールバックで読める。
カードをクリックすると今までどおり3章の全文がポップアップで開く（ドリルダウンの入口は変えていない）。
bulletsを持たない古い行は、`index.vue` の `cardBullets()` が各章の最初の1文（`breakSentences` で文末ごとに
改行済みなので1行目だけで文が完結している）を代わりに出すフォールバックを持つ＝考察そのものが無い
（新規で記事が集まっていない）ときだけ「まだ記事が集まっていません。」になる。**bulletsもフォールバックも
文字数での機械的な切り詰めはしない**＝「…」で尻切れにすると内容が完結して見えず読みづらいため、
長さはプロンプトの指示（15字程度）だけに任せ、はみ出しはカード側の折り返しで吸収する）。
**Markdown記法（`**`等）の混入と「1文ごとに改行」はプロンプトの指示だけでは守られないことを実測で確認済み**なので、
どちらも `news-ai.ts` の `stripMarkdown()` / `breakSentences()` でサーバー側が機械的に矯正する
（新しく考察系のプロンプトを足すときも、フォーマット指示は出力側の後処理とセットで考えること）。

**動作確認**: ローカルdevは D1 が使えないので `/news` は動かない。デプロイ後にページの「いま収集する」で確認する。
ログは `wrangler tail` の `[news]` 接頭辞か、ページ下部の実行ログ（`news_runs`）。

**費用**（実測 2026-09-06、Haiku 4.5）: Claude API だけ。同じ記事で Sonnet 5（$2/$10 per MTok）と比較したところ
品質差はほぼ無くトークン数もHaikuの方が少なく済み（入力3,122→2,190）、1記事あたり約1.48円→約0.58円に下がったため
`NEWS_MODEL` は Haiku 4.5（$1/$5 per MTok）を既定にしている。15フィード・1日あたり約18件のペースで
**月180〜280円**の見込み（要約とは別に潮流の考察も1潮流あたり1回/日呼ぶが、こちらは軽い呼び出しなので誤差程度）。

作りの前提（触る前に読むこと）:

- **OpenAI の記事ページは 403 を返す**ので本文は取得できず、RSSの `description`（平均156字）だけで要約している。
  逆に DeepMind は `description` が空で記事ページからは取れる。**どちらのフォールバックも消さないこと**
- **OpenAI のフィードは1000件超を返す**。`NEWS_LOOKBACK_DAYS`（5日）と `NEWS_MAX_PER_RUN`（20件）が
  費用の安全弁で、これを外すと初回実行で全件を要約してしまう。裏を返すと日数を超えて止めると、その間の記事は取りこぼす（拾い直さない）。
  ただし実際に1回の実行で処理される件数は `NEWS_MAX_PER_RUN` より少ないことが多い。
  `news-run.ts` の `SUBREQUEST_BUDGET` が実消費した subrequest 数を見て安全マージンに達したら
  その回の残りを打ち切る（未保存の記事は次回の実行で自然にもう一度拾われるので、失敗時の再試行と同じ扱い）
- D1 の書き込みは `db.batch()` でまとめて1回の subrequest に収める（`ensureNewsTables` / `loadKnownUrls` /
  記事の保存 / 潮流考察の材料取得、すべて）。**batch() は1文でも失敗すると全体がロールバックされる**ため、
  「初回だけ成功して以降は必ず失敗する」類の文（列追加のALTERなど）は同じbatchに混ぜないこと
- 記事の重複判定は `news_items.url` の UNIQUE 制約。処理済みURLの一覧ファイルは持たない
- **フィードの `pubDate` が非標準形式のことがある**（Fierce Healthcare の `"Sep 4, 2026 9:44am"` は am/pm の前に
  スペースが無く `Date.parse` が失敗する）。`news.ts` の `toIso()` で正規化しているので、新しいソースを足すときも
  日付が全部空になっていないか一度確認する
- AIの潮流分類がハルシネーションで5つのID以外を返したら `NEWS_FALLBACK_CURRENT`（`knowledge-work`）に丸める
- プレビュー環境は `[env.preview.triggers] crons = []` で cron を止めてある。
  triggers は継承されるキーなので、これが無いと本番と同じDBに対して二重に走る（mlb-sync も同様）
- cron の曜日は UTC 基準。平日だけにするなら `0 22 * * 0-4`（UTC 日〜木 ＝ JST 月〜金）
- **メールをやめた経緯**: Worker から SMTP は張れず、Cloudflare Email Sending は公式ドキュメント上
  「Workers Paid プランで利用可能」（月$5）。要約代が月180〜280円なのに通知だけで数倍かかるため見送った。
  再検討するなら Resend の無料枠を HTTP で叩くのが近い（差し替えは送信部分だけで済む作りにしてある）

### farm-news（農業×AI専門ニュース）のセットアップ

2026-09-14、news の「農業・畜産とAI」潮流を切り出す形で追加。**news との最大の違いは2つ**：
①**外部公開・ログイン不要**（news は自分専用のログイン必須ページ）②**潮流アーカイブを持つ**
（news の `news_currents` は1潮流1行で履歴を残さないが、farm-news は月次/年次のスナップショットを
`farm_news_trend_snapshots` に蓄積し、①最新ニュース→②今後の潮流予測→③潮流アーカイブ（直近6ヶ月は
月ごと、それより前は年ごと）の3段構成で見せる。要求元はユーザー本人）。

**公開ページなので認証の作りが news と違う**。news は各ページ/APIが `getSessionUser`（users/sessions
Cookie）を個別にチェックする作りだが（このリポジトリにグローバル認証middlewareは無い＝チェックを書かなければ
そのページ/APIは誰でも見える）、farm-news は `/api/farm-news` にそのチェックを書いていないので誰でも読める。
**手動実行（news の「いま収集する」ボタンに相当）はUIに置かず、秘密キーをヘッダーに付けてコマンドから叩く**
運用にした（`NUXT_FARM_NEWS_ADMIN_KEY`。`server/utils/farm-news.ts` の `requireFarmNewsAdmin` が
`x-admin-key` ヘッダーを見る）:

```bash
curl -X POST https://<host>/api/farm-news/run -H "x-admin-key: $NUXT_FARM_NEWS_ADMIN_KEY"                    # 収集・要約・分類
curl -X POST https://<host>/api/farm-news/run-trends -H "x-admin-key: $NUXT_FARM_NEWS_ADMIN_KEY"              # 潮流の考察・予測を更新
curl -X POST https://<host>/api/farm-news/archive-run -H "x-admin-key: $NUXT_FARM_NEWS_ADMIN_KEY"             # 潮流アーカイブを生成（月初cronを待たずに実行可）
curl -X POST https://<host>/api/farm-news/historical-backfill -H "x-admin-key: $NUXT_FARM_NEWS_ADMIN_KEY"     # 過去年アーカイブをWeb検索で生成（下記参照。複数回叩く必要あり）
```

cron は news と同じ理由（Cloudflare Workers の subrequest 上限）で処理を分けている。
digest/trends は news と同じ3日に1回だが**時刻を30分〜1時間ずらしている**（同時に走らせる必要はなく、
ずらしておいた方が万一の輻輳やログの追いやすさで安全という判断。UTC 23:00/23:15＝JST翌朝8:00/8:15）。

**archive（潮流アーカイブの生成）は cron 登録していない＝上記の `archive-run` を手動で叩く運用**。
2026-09-14、archiveをcron登録しようとして**Cloudflare Workers Freeプランの「cronトリガーはアカウント
全体で5個まで（Workerごとではない）」に実際に当たった**（mlb-sync・news-digest・news-trends・
farm-news-digest・farm-news-trendsで既に5個。6個目の登録で `10072` エラー）。Paid化（月$5）と
削減の二択をユーザーに確認し、削減を選択。月1回でよい処理なのでコマンド実行で十分と判断した
（詳しい設計は `server/utils/farm-news-run.ts` の `runFarmNewsArchive` 冒頭コメント参照）。
**6個目以降のcronを追加したくなったら、まず既存を間引けないか検討すること**（wrangler.tomlにも同じ注記あり）。

初回セットアップはテーブル作成だけ:

```bash
wrangler d1 execute whisper-db --remote --file src/server/db/062_farm_news.sql
```

加えて `wrangler secret put NUXT_FARM_NEWS_ADMIN_KEY` で管理キーを設定すること（未設定だと手動実行APIは
常に401を返す＝安全側に倒れる。cron経由の自動実行には影響しない）。

**潮流は4つ**（`src/utils/farm-news-currents.ts`）：精密農業・センシング／農業ロボット・自動化／
農業データ・経営／政策・気候とAI。news と同じく記事単位でAIが分類する（ソースと潮流は固定対応ではない）。
**当初は畜産・酪農のスマート化（livestock-ai）／スマート漁業・林業（fishery-forestry）を含む6潮流だったが、
2026-09-14に本人の「農業だけでいい、酪農や漁業はいらない」という要望で2つ削除した**（id は欠番のまま
詰めていない。D1に残っていた該当記事・考察も削除済み）。

**ソースは8つ**、2026-09-14時点で実際にHTTPで疎通確認済み（AgFunderNews・Global AgTech
Initiative・Future Farming・CropLife・Farm Progress・Modern Farmer）。**畜産専門の Feedstuffs・
BEEF Magazine は上記の潮流削除にあわせて外した**。漁業・林業（旧 fishery-forestry潮流）専用のソースは
そもそも見つけられていなかった（IntraFish・SeafoodSource・TheFishSite・DairyGlobal等はいずれも404/403で不通）。
**2026-09-15、日本語ソースを2つ追加**（SMART AGRI・AGRI JOURNAL）。以前は「日本語ソースの候補も全滅」
としていたが、これは agri-navi.com / smartagriexpo.jp の2件しか試していなかっただけで、改めて探すと
両方とも実際に生きたフィードを持っていた（＝日本語ソースが無いのではなく探し方が甘かった）。
**SMART AGRIのフィードURLは`/feed`ではなく`/rss`（Atom形式）**＝`/feed`はWordPressの定番パスだが
このサイトはWordPressではなく、叩くとアイテム0件の空チャンネルを返すだけの罠。正しいURLはページの
`<link rel="alternate" type="application/rss+xml" href="/rss">`から見つけた。ソース候補と不通の詳細は
`farm-news-sources.ts` 冒頭コメント参照。

**潮流の考察は news と同じ3章構成だが、farm-news では「これから（予測）」を主役にしている**
（`FARM_NEWS_TREND_SECTION_TITLES`＝ここまでの流れ／新着トピック／これから（予測）。プロンプトで
outlookを「根拠とセットで厚めに書く」よう指示している。トーン・後処理（Markdown除去・改行矯正）は
news の `news-ai.ts` と同じ仕組みを `farm-news-ai.ts` に複製している）。**2026-09-15、trend/outlookの
どちらかで必ず日本の状況に触れるようプロンプトへ指示を追加した**（記事のほとんどが海外発なので、
材料に日本発の記事があればそれを使い、無ければ「日本では目立った動きが少ない＝情報が少ない」というヒントを
断定を避けつつ書かせる。Web検索は使わせていない＝3日に1回のcronで動く軽い処理なので、subrequest予算と
コストを増やしたくないため。日本語ソース追加で材料そのものに日本発の記事が混ざり始めれば自然に効いてくる想定）。

**潮流アーカイブが news に無い新機能**。`farm_news_trend_snapshots`（period_type='month'|'year'）に
一度生成したスナップショットは基本上書きしない（アーカイブとして固定する設計。作り直すときは該当行を
明示的にDELETEしてから `archive-run` を叩く）。生成ロジック（`runFarmNewsArchive`）：
①記事がある月のうち、今月より前でまだスナップショットが無いものを古い順に最大 `FARM_NEWS_MAX_MONTH_SNAPSHOTS_PER_RUN`
（3）件生成 ②月次スナップショットがある年のうち、その年が完全に過去になっていて（今年より前）まだ年次が
無いものを最大 `FARM_NEWS_MAX_YEAR_SNAPSHOTS_PER_RUN`（2）件生成（その年の月次スナップショットの本文を
材料にAIがまとめ直す）。**ページ側の表示は「直近 `FARM_NEWS_ARCHIVE_RECENT_MONTHS`（6）ヶ月は月次カード、
それより前は年次カード」だが、年次スナップショットがまだ無い年（今年のように、過去になっていないため
生成されない年）は、その年の月次スナップショットをそのまま個別カードにフォールバック表示する**
（`pages/farm-news/index.vue` の `archive` computed）＝データを欠落させないための救済で、年が明けて
`archive-run` が年次を生成すれば自動的に1枚の年次カードへ切り替わる。**運用開始直後は記事もアーカイブも
空**（半年ほど記事が積み上がるまで月次カードは1枚も出ない）。

**①最新ニュースは重要度3以上だけ表示する（既定）**。2026-09-14に一度、重要度フィルタを撤廃し
`filtered`（ソース・キーワード絞り込み後）の中から**重要度が高い順（同点は新しい順）に上位5件
（`TOP_ITEM_COUNT`）は常に全文表示**、**それ以外は `<details>`/`<summary>` で折りたたみ**表示にしていたが
（`pages/farm-news/index.vue` の `topIds`。この表示自体は今も残っている）、**2026-09-15に
`FARM_NEWS_MIN_IMPORTANCE`（3）を使った絞り込みを復活させた**。理由は「農業全般」も拾ってしまう
ソース構成のせいでAI/IoTと関係の薄い記事が①に混ざって見える、という指摘（下記の重要度プロンプト強化と
セットの対応）。絞り込みポップアップの「重要度」チップ・APIの `minImportance` フィールドも復活済み
（`filtered` が `sourceId`/`keyword` に加えて `minImportance` でも絞り、その結果の中から上位5件を
`topIds` で全文表示する＝2つの仕組みは併存）。news 側の同名の仕組みとは独立している。

**重要度の判定基準に「AI/IoT関連度」を明示的に足した**（2026-09-15、`farm-news-ai.ts` の
`summarizeArticle` システムプロンプト）。CropLife・Farm Progress・Modern Farmerのようなソースは
そもそも「農業全般」メディアでAI専業ではないため、天候・相場・品種・一般的な栽培技術のような
デジタル化と無関係な記事も候補に混ざる（収集段階でのジャンル事前フィルタは無い＝直近5日以内なら
ジャンル問わず候補になる）。加えて記事ごとに4潮流のどれかへ強制分類する仕組みのため、無関係な記事でも
一番近そうな潮流ラベルが付き、「タイトルが潮流のテーマとズレて見える」という不満につながっていた。
実際にはズレて見える記事ほど重要度が低く付く傾向があった（デジタル化の材料が薄いと判断されるため）ので、
根本原因を突く形で「AI/IoTと明確に関係しない記事は重要度1〜2に抑える」という基準を明文化した
（=上の重要度3以上フィルタと組み合わせて、ズレた記事が①に出にくくなる）。ソース自体は絞らず残した
（CropLife等もAI/IoT関連の記事を出すことはあるため、プロンプト側の判定で対処する方針）。

**過去アーカイブ（Web検索バックフィル）が2026-09-15に追加**。③潮流アーカイブは元々「実際に収集した記事」
だけが材料で、RSSは直近の記事しか配信しないためサイト運用開始（2026-09-14）より前の年は
`runFarmNewsArchive` では永久に埋まらない。過去5年ぶんの潮流も見たい、という要望で
`runFarmNewsHistoricalBackfill`（`server/utils/farm-news-run.ts`）を新設し、まだ実データの無い年
（今年から `FARM_NEWS_HISTORICAL_YEARS_BACK`＝5年前まで）を対象に、年ごとに1回だけ
`synthesizeHistoricalYearSnapshot`（`farm-news-ai.ts`）が Claude の Web検索（`anthropic.ts` の
`callClaudeText` の `webSearch` オプション。既に guesthouse のお客様チャットで使っている仕組みを流用）で
調べ物をして年次スナップショットを直接生成する（1500日を日次/月次で埋めるのは費用に見合わないため、
年単位の粗いサンプリングにした。5年分なので最大5回、1回の実行につき `FARM_NEWS_HISTORICAL_MAX_SNAPSHOTS_PER_RUN`
（2）年ぶんまでしか作らないので `historical-backfill` を複数回叩く必要がある）。このプロンプトでも
「日本の状況に必ず触れる、無ければ情報が薄いこと自体をヒントとして書く」よう指示している。
モデルは軽い分類作業用の `FARM_NEWS_MODEL`（Haiku）ではなく `anthropic.ts` の既定（Sonnet 5）を使う
（実行頻度が低い一回性のバックフィルなので、調べ物の質を優先）。**生成したスナップショットは
`itemCount: 0`**（実データが無いことの目印。ページ側は `itemCount === 0` を「Web検索をもとにした
振り返りです（当時の収集記事はありません）」という文言に読み替える＝`archiveCountLabel()`）。
cron登録は無い＝Freeプランのcron上限（既存5個）に既に当たっているため、`archive-run` と同じく
手動実行のみ。**`archive` computed のバグも同時に直した**＝年次スナップショットだけあって月次が
1件も無い年（＝このバックフィルで生成した年）が `years` の集合に入らず older 一覧から丸ごと
消えていたため、`yearSnaps` のperiodKeyも `years` に合流させるよう修正した。

**動作確認**: news と同じくローカルdevはD1が使えないため `/farm-news` は動かない（デプロイ後に管理APIを
`curl` で叩いて確認する）。ログは `wrangler tail` の `[farm-news]` 接頭辞。
